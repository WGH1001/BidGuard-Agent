# E17 · F2 发现锚点页码定位卡

> 状态：待派发 Gemini（**必须等 E15 交付后串行派发**——同动 worker.py finding 落库区）｜ 立卡：2026-11-09 ｜ 基线：E15 合入后的最新 commit
> 来源：用户指出"单价/数量/合价三个数字集中出现在报价表同一行，F2 凭什么做不了页码"——架构侧原判"F2 不改"作废，本卡采纳用户方案

## 1. 背景与方案

F2 的发现虽由沙盒复算产生，但其输入（分项名称、单价、数量、合价）全部来自报价表真实文本，且**集中在同一行**。方案：以**分项名称行文本为锚点**反查展平全文 offset，走 E6 双轨页码链换算页码——不是硬造页码，是真锚定。

## 2. 改动清单

1. **core/price_extractor.py**（锚点信息输出）：
   - items dict 已含 `name`；findings 生成处（TOTAL_MISMATCH / CAP_EXCEEDED / AMBIGUOUS_BID_TOTAL / CROSS_TABLE_BID_WARNING 等）补充 `anchor_text` 字段：
     - ITEM_ARITHMETIC 类单行发现 → anchor_text = 该行分项名称（首选）或"名称+金额"组合串；
     - 表级发现（TOTAL_MISMATCH 等）→ anchor_text = 开标一览表总价行文本或该表首个明细行名称；
     - 找不到稳定锚文本的 finding → 不输出 anchor_text（诚实缺省）。
2. **backend/worker.py**（F2 写库处，约 L338-395，E15 改造后的最新版）：
   - 对带 anchor_text 的 F2 finding：在 bid_parsed.text 中搜索锚文本首次出现的 offset（找不到再试全库 bid 文本；均找不到则保持 quote=None/page=None 诚实回退，与 F4 五级降级链同精神）；
   - 写入 `quote=锚文本`、`quote_offset=offset`、`page=offset_to_docx_page(offset, build_docx_page_spans(bid_abs))`（E15 已在流水线内建好的页码索引直接复用）、`quote_verified=True`（确为原文子串）；
   - 无 anchor_text 的 finding 保持现状（章节名已可定位）。
3. **前端零改动**：formatPageOrOffset 已兼容 page/offset/无 三态。

## 3. 验收标准

1. pytest 新增：① 构造含 ITEM_ARITHMETIC 的报价表 docx → 对应 finding 的 quote 为该行分项名称原文子串、page 非空；② 锚文本被合并单元格拆散的形态 → 诚实回退无 page、零报错；③ 芜湖无为真实语料复测：AMBIGUOUS_BID_TOTAL 等 findings 带 page 或诚实回退（断言不硬造）；
2. 全量 pytest（151 + 新增）零回归全绿；
3. 前端走查：F2 卡片显示"第N页(...)"且点击跳转定位到对应页（复用 F4 既有跳转链）。

## 4. 铁律

- 锚定失败必须诚实回退"—"，严禁定位不到硬造页码；quote 必须过 verify_quote 原文子串核验；commit 中文；严禁动 E13/E14 去重与汇总行判定语义。
