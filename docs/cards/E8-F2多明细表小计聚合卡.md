# E8 · F2 多明细表小计聚合卡（分表明+小计+汇总表排版防误判）

> 状态：**已派发**（2026-11-07，派发包 `派发归档/E8派发汇总.txt` 1772 行，与仿真语料滚动并行）。
> **设计原则（沿用 E7 用户令）**："每个平台/分包一张明细表 + 各带小计行 + 一张汇总表"是真实标书
> 的常见合法排版——系统必须适配，严禁要求用户合并成一张大表。

## 事故复盘（无锡梁溪仿真标书实锤，commit 前验收发现）

文档报价结构（算术全部正确，逐表人工验算过）：

| 表 | 内容 | 金额 |
|---|---|---|
| 表#2 汇总表 | 五大分项金额 + 合计行（无单价/数量列） | 合计 2,986,000.00 = 总报价 ✓ |
| 表#3 馆藏平台明细 | 7 子系统 + **小计**行 | 小计 1,180,000.00 ✓ |
| 表#4 档案室平台明细 | 5 子系统 + **小计**行 | 小计 860,000.00 ✓ |
| 表#5 互联网+AI 明细 | 7 模块 + **小计**行 | 小计 706,000.00 ✓（=汇总表 286,000+420,000 两分项之和）|
| 表#6 迁移运维明细 | 5 项 + **小计**行 | 小计 240,000.00 ✓ |
| 表#1 开标一览表 | 投标总报价 | 2,986,000.00 ✓ |

F2 实测报 2 条 error：`分项合价累加=2986000，与明细表合计 1180000 不一致`——**table_total 被第一张分表的"小计"抢占**。

## 根因（`core/price_extractor.py` 行级）

- **行 740-752 汇总行规则**：`if table_total is None or '小计' not in row_full_text: table_total = ...`——首张遇到汇总行的表先占坑；"小计"行只在尚无值时生效，且**没有任何"多张分表明"的场景聚合逻辑**；
- **行 550 附近的表头识别**：`_detect_header_map` 要求单价/数量等列齐全——汇总表（分项金额+合计，无单价数量列）进不了明细解析路径，其合计行只能落入逐格扫描（行 574+），而那里 E7 之后限价语境排除已生效，汇总表合计恰含"最高限价"语境词时反而可能被跳过；
- 结果：全文档唯一的权威"合计 2,986,000"（汇总表）无人认领，第一张分表的小计 1,180,000 冒名顶替。

## 修复设计（四条）

1. **多分表小计聚合（核心）**：明细解析路径按表分组收集"小计"与"合计"——当文档存在**多张**含小计/合计行的明细表时：若存在非"小计"的"合计/总计"行所在表，且该表同时含多个分项行（即全量明细表），以其为 table_total；否则 **table_total = Σ各分表小计**（Decimal 累加）。同表内既有小计又有合计时，合计优先。
2. **汇总表识别与权威源**：无单价/数量列、但含"分项名称+金额+合计行"的表识别为"分项汇总表"——其合计行可直接作为 table_total（优先级最高，与 bid_total 比对的权威源）；汇总表各行金额同时与 Σ小计交叉核验，不一致出 warning。
3. **防双重计数**：聚合 Σ小计时须防同一张表被两条路径重复计入（单表既有小计又进了汇总识别）；跨表去重以表元素引用为键。
4. **比对语义不变**：聚合后的 table_total 与 bid_total/开标一览表比对逻辑维持现状——不一致仍报 error（此时是真错误），None/歧义时 warning。

## 验收标准

1. **全量 pytest 零回归**（121 项基线 + 本卡新用例）；
2. **新用例至少覆盖**：①单表全分项+合计（现状不得误伤）；②多分表+小计+无汇总表（Σ小计）；③多分表+小计+汇总表（取汇总表合计，Σ小计交叉核验一致）；④Σ小计与汇总表合计不一致（warning 非 error）；⑤小计行里混限价语境词（继承 E7 排除）；
3. **实弹试金石**：无锡 v1 原稿（多分表排版，不返工）输入后 F2 应 **0 error**（table_total=Σ小计=2,986,000 与总报价一致）；
4. **11 份真实语料回归**：price_cap 基线 11/11 与既有 F2 结果不变；滁州/科技/固废/病理四份已过仿真标书 F2 依旧零告警。
