# E11 · 体检任务耗时统计与前端展示卡

> 状态：待派发 ｜ 立卡：2026-11-09 ｜ 来源：用户实测反馈"F2-F4 这里感觉特别慢"

## 1. 背景与问题

用户实际跑体检任务时感觉特别慢，但系统当前**没有任何耗时记录**：慢在 F1 的大模型红线提取？F4 的逐条勾稽？还是解析环节？完全不可观测，无法定位优化点。

当前流水线（`backend/worker.py` `_run_pipeline`）按顺序执行：
1. **阶段 1 extracting**：F1 招标红线与 ★/▲ 提取（有 Key 时走 `extract_tender_with_llm`，LLM 调用，常为大头）；
2. **阶段 2 checking**：`run_price_check`（F2）→ `parse_document`（投标书解析）→ `scan_qualifications`（F3）→ `run_response_check`（F4，含 LLM 与混合检索，逐条款核验，通常最大头）；
3. **阶段 3 grading**：发现汇总落库。

`BidCheckTask` 模型只有 `created_at`，无 started_at / finished_at / 分阶段耗时；前端任务列表与详情页因此无任何耗时显示。

## 2. 改动清单（自包含，实现者无需读其他卡）

1. **数据模型**（`backend/models.py`）：
   - `BidCheckTask` 新增 `started_at`（DateTime, nullable）与 `finished_at`（DateTime, nullable）；
   - 新增 `duration_json`（Text, nullable，JSON：`{"f1_ms": ..., "f2_ms": ..., "f3_ms": ..., "f4_ms": ..., "grading_ms": ..., "total_ms": ...}`，缺失阶段记 null）。
   - 注意 schema 演进：项目无 Alembic，`Base.metadata.create_all` 只建新表不加列。需按项目现有库初始化方式保证**老库平滑加列**（SQLite/PostgreSQL 均为 `ALTER TABLE ... ADD COLUMN`，启动时探测缺列补齐；已有任务行新列取 NULL 即可）。
2. **worker 记录**（`backend/worker.py` `_run_pipeline`）：
   - 流水线开头写 `started_at`（UTC），并 emit SSE 帧带 `started_at`；
   - 各阶段用 `time.perf_counter()` 包裹计时（F1 提取 / F2 / F3+解析 / F4 / grading 分别计），结束写 `finished_at` 与 `duration_json`；
   - 失败路径（异常终态 error）也要尽量写入 `finished_at` 与已完成的阶段耗时，便于分析卡死点；
   - 重新体检（`_reset_task_for_rerun`）时清空旧耗时字段。
3. **API 透出**（`backend/routers/checks.py`）：任务列表与详情的 Pydantic Out 模型增加 `started_at` / `finished_at` / `duration`（duration_json 解析后的 dict 或 null）。
4. **前端展示**（`frontend/src` 体检任务列表 + 任务详情）：
   - 任务列表：终态任务显示总耗时（如 `2分18秒`，<1s 显示 `0.8s`）；
   - 任务详情：显示分阶段耗时（F1 / F2 / F3 / F4 / 汇总），建议横向堆叠条或简单列表，最慢阶段高亮；
   - 运行中任务不显示耗时（或显示已进行时间，实现取简）。

## 3. 验收标准

1. pytest 新增用例：跑完一条同步体检任务后，断言 `started_at`/`finished_at` 非空、`finished_at >= started_at`、`duration_json` 各阶段数值非负且 `total_ms >= max(各阶段)`；error 终态任务 `finished_at` 也被写入；
2. 老库（无新列的已有 SQLite/PG 库）启动不报错、自动补列；
3. 前端走查：列表与详情正确显示耗时，全绿无 TS 报错；
4. 全量 pytest 131 项 + 新增用例全绿。
