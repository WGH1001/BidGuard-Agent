# E4 · 法规库与法条核验卡

> 背景：系统各防线输出的"法律依据"目前是写死的静态字符串，用户无法核对原文——
> 这违背溯源铁律的延伸原则：**给用户的法律依据也必须可溯源**。本卡建 BidGuard 自己的
> 法规库（轻量版，聚焦招投标领域），支持条文浏览检索、法条真伪核验、种子导入与官网一键更新。
> 种子数据已就位：`data/corpus/regulations/` 下 4 部法律 JSON（继承自上项目的
> `data/knowledge/official/`，格式 `{law:"《...》", articles:[{article:"第一条", content:"..."}]}`）。

## 2. 铁律

1. 既有 9 表、既有端点、既有 94+ 项测试零回归；公共签名只增不改；
2. **核验三态是本卡灵魂**：exact_match 才可标"已核验"；LLM 严禁对真伪下结论——宁可 unverifiable，不许编造；
3. 爬取失败必须诚实报错并引导手动导入，禁止静默吞错或拿 LLM 补内容；
4. 不新增 pip 依赖（requests/lxml/PyYAML 均已在 requirements 钉死版本内）；
5. TS 5.6 严格类型禁 any；视觉延续 RulesAndCertsView 既有页签风格；
6. 每个文件完整全文，严禁截断；**总量约 3300 行，一次性连续输出全部 13 个交付物，不分批**（若逼近单次输出长度上限，必须在文件边界停下说"待续"，严禁把一个文件切成两半）。

## 3. 种子数据与源配置（架构侧已备好，勿改结构）

`data/corpus/regulations/`：
- **4 部 JSON 种子**（导入格式依据）：招标投标法（68 条）、政府采购法、反不正当竞争法、中小企业款项支付条例——`{law:"《...》", articles:[{article:"第X条", content:"..."}]}`，init 幂等导入；
- **originals/ 下 4 份官方原文**（import 端点的真实测试料）：招标投标法/政府采购法/政府采购法实施条例（docx）+ 财政部令第 87 号（6.4MB PDF，**大概率扫描版，import 必须走 parser 的 OCR 链路**）——**import 端点因此必须支持 json/txt/docx/pdf 四种格式**（PDF 按既有 parse_document 链路处理，扫描件走 RapidOCR），导入后按"第X条"正则切条入库。

`config/regulation_sources.yaml`（已建）：6 个源的 url 均为 `TODO_USER_FILL` 占位——用户找官方 URL 后填入即可用"检查官网更新"；**占位符状态下 crawl 端点必须对该源诚实报"源未配置"**，不得报 500，其余源不受影响。§1 交付物中该文件不再由你新建，改为在其基础上补 crawl 消费逻辑（文件本身已存在）。
