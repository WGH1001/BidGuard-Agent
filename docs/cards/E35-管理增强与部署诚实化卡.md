三件事收口：① 部署诚实化——客户生产库被强制写入我方演示部门/账号（部署级 bug，优先级最高）；② 管理完整性——部门/账号重命名 + 禁用账号隐藏；③ 证照预填诚实化——文件名兜底冒充识别结果、弹窗假日期默认值、长期有效证件无处安放。

## 3. 改动设计

### §3.1 种子分层初始化（最高优先，部署级）

`init_db` 拆两层，**无论开关状态都幂等确保底线可登录**：

- **`SEED_DEMO_DATA=0`（生产）**：仅当库中无租户/管理员时创建——1 个中性默认部门（名称读 `DEFAULT_TENANT_NAME` 环境变量，缺省 `'默认机构'`）+ 1 个 `admin`（密码读 `ADMIN_INITIAL_PASSWORD`）+ 1 条中性空规则（`buyer_name=''`、`price_cap=None`、`open_date=None`、`required_social_months_json=[]`）；**绝不建** liming、第 2/3 演示部门、假甲方规则、演示证照；
- **`SEED_DEMO_DATA=1`（开发/测试，默认值不变）**：现状全量保留（`SEED_TENANTS` + admin/liming + 演示规则/证照），**286 项既有测试零回归**（test_backend_routers 等依赖 liming 的用例不受影响）；
- 实现建议：`ensure_bootstrap_admin()`（底线层，无条件幂等调用）与 `seed_demo_data()`（演示层，按开关）拆成两个函数；L337 内层遗留 gate 语义化清理；
- 配套：`.env.example`、`deploy/.env.docker.example`、`docker-compose.yml`（透传 `DEFAULT_TENANT_NAME`）、`DEPLOY.md` 生产部署清单更新（从此生产三件套简化为 `ADMIN_INITIAL_PASSWORD` + 可选 `DEFAULT_TENANT_NAME`）。

### §3.2 部门重命名

- `PATCH /api/auth/tenants/{tenant_id}`：`require_admin`、名称非空 + 长度上限、`409` 重名（排除自身）、`rename_tenant` 审计；
- 无副作用：租户全链以 `tenant_id` 被引用，`name` 仅展示字段。

### §3.3 用户重命名（display_name + username）

- `PATCH /api/auth/users/{user_id}` 扩展可选 `username`：`_USERNAME_RE` 校验同创建口径、`409 USERNAME_EXISTS`（排除自身）、审计记 `old_username`/`new_username`；
- **`backend/auth.py` 真漏洞补齐**：`get_current_user` 在 `db` 为 `Session` 且 `user_obj is None` 时**严禁**跌落 L333 兜底对象，必须立即抛 `401 USER_NOT_FOUND`（"账号不存在或用户名已变更，请重新登录"），仅保留 `db is None` 的纯无状态单测路径；
- **语义锁死（不做跨端迁移）**：改 `username` 后旧 token（`sub=旧名`）查库即 401 强制重登；F7 置顶按员工本地 localStorage 分键、管理员端无法代迁——UsersManageView 提交前弹确认明示"该员工需重新登录，本地置顶会话需重新置顶"；改的是当前登录管理员自己则前端自动登出重登；
- `display_name` 改名已支持（PATCH 现有字段），无新增。

### §3.4 已禁用账号隐藏筛选

- UsersManageView 列表加「显示已禁用」开关，**默认隐藏**；列表量小，纯前端过滤即可，后端 GET /users 不动。

### §3.5 证照预填诚实化 + 长期有效

1. **文件名兜底标注**：`CertificateParseOut` 增 `cert_name_source: 'ocr' | 'filename_fallback' | null` 与 `is_long_term_hint: bool`；前端 `filename_fallback` 时显示「名称来自文件名兜底，请人工核对」；
2. **弹窗假日期清除**：清除 [RulesAndCertsView.vue](file:///e:/agent/BidGuard-Agent/frontend/src/views/RulesAndCertsView.vue) L120（`'2026-11-20'`）与 L138（`'2027-06-30'`）两处硬编码，默认空串 `''`，强制手填真实日期或勾选「长期有效」；
3. **长期有效模型（老库平滑迁移）**：`models.py` 新增 `is_long_term BOOLEAN NOT NULL DEFAULT 0`（走既有 `_ensure_table_columns_generic` 加列，不动 SQLite 的 NOT NULL 约束）；`CertificateUpsertRequest` 允许 `valid_until: Optional[date] = None` + `is_long_term: bool = False`（非长期且缺日期抛 `422`）；勾选长期时 `valid_until` 落哨兵日 `9999-12-31`，接口层（`CertificateOut` & `MatchedLedgerCertOut`）与审计日志 `detail_json` 统一返回 `is_long_term=True` + `valid_until=None`（及 `days_remaining=None`），[RulesAndCertsView.vue](file:///e:/agent/BidGuard-Agent/frontend/src/views/RulesAndCertsView.vue) 与 [ExtractView.vue](file:///e:/agent/BidGuard-Agent/frontend/src/views/ExtractView.vue)（L425 `ledgerStatusMeta` 与 L891 匹配脚标）均显示「长期有效 / 台账有效 · 长期」——假日期绝不外泄；
4. **下游对账与大盘适配**：`_cert_to_out` 与 `dashboard.py` 在 `is_long_term=True` 时恒 `status='valid'` / `is_expired=False` / `is_expiring_soon=False`（`expiring_only=True` 不误召回）；`qualification_scanner.match_required_certificates_with_ledger` 对长期证照直接判 `valid`（消除 L682 `continue` 误判，且 L708 `candidates.sort` 按 `(status_rank, 1 if is_long_term else 0, days_remaining or 0)` 排在有限日期前、避免 `None vs int` 比较抛 `TypeError`）；`_extract_cert_fields_from_text` 增 `长期|永久|无固定期限` → `is_long_term_hint=True`。
