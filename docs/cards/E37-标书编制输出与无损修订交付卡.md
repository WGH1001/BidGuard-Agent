## 1. 业务背景与双引擎边界

针对“自动输出标书”的三种真实工程语义，本卡将其统一梳理为“先期编制输出 + 后期审改定稿”两个严格隔离的底座：

1. **正向生成引擎（`core/bid_composer.py` · F8 模块，涵盖 ① → ②）**：
   - **V1（本卡实装落地）**：上传《招标文件》（或直接复用已有 `pre_check`/F1 提取结果），联合租户 `CompanyCertificate` 企业证照台账与 `BidRuleConfig` 基础信息，自动装配生成一份**结构完整、偏离表填好、证照清单/原件关联到位、绝不串名、缺项显式 `[待人工填报]`** 的《投标文件初稿骨架.docx》；
   - **V2（统一蓝图扩展位，支持传参即用）**：同一套 `BidBlueprint` 章节槽位引擎预留 `'rag_knowledge'` 策略接口——当用户在本卡工作台额外勾选/上传企业历史优秀标书参考文档（`knowledge_files`）时，按评分细则小节做局部检索对齐并生成参考段落（带 `verify_quote` 原文核验与 `[参考片段·待人工确认改写]` 标黄提示；未接知识库或无引用则输出编写提纲骨架，严禁编造参数/金额）。
2. **原位无损修订导出（扩展 `core/redline.py` · 对接 ③ 采纳整改定稿）**：
   - 用户在 **F2–F4 体检台（`CheckDetailView`）** 将部分风险项点击「采纳整改」后，现有 `/api/reports/{task_id}/redline` 只产出带红色批注气泡的审阅件；
   - 本卡在 `core/redline.py` 新增 `export_clean_revised_docx(...)`：在保留原 `.docx` 封面、页眉页脚、签章定位与复杂表格排版的前提下，**仅对具备明确安全原位替换规则的已采纳发现（如 F3 串名清理、明确旧年份/错误数值修正）执行 run 级无损替换**并彻底移除批注 XML 标签，产出可提交的《修订定稿版投标书.docx》；对于整段漏应答等结构性缺失，宁缺毋滥，随单附出《尚待人工补写事项清单》而不破坏原稿结构。

## 3. 核心设计方案

### §3.1 正向编制引擎：`core/bid_composer.py`（蓝图 IR + 槽位填充策略）

1. **统一数据结构 `BidBlueprint` 与 `BlueprintSection`**：
   - `BlueprintSection` 字段：`section_id`、`title`、`slot_type`（`'qualification_checklist' | 'cover_and_letter' | 'price_placeholder' | 'deviation_table' | 'scoring_response_outline' | 'cert_ledger_appendix'`）、`fill_mode`（`'deterministic' | 'cert_ledger' | 'deviation_table' | 'outline_stub' | 'rag_knowledge'`）、`tender_requirements`（关联招标原文与 ★/▲ 条款列表）、`content_blocks`、`needs_manual_items`、`source_refs`。
2. **V1 确定性蓝图装配（0 幻觉保底）**：
   - **封面与投标函/报价表占位**：从 `checklist`（`open_date` 等）、招标原文及 `BidRuleConfig`/F1 抽取结果带出招标项目名称、项目编号、开标日、最高限价提示；**我方投标总价/单价栏强制填充 `[待人工核报金额，当前参考限价：X 元]`，严禁 AI 自填报价**；
   - **资格审查与企业证照匹配节**：把招标所需证照清单（`required_certificates`）与租户 `CompanyCertificate` 台账逐条对接——台账有效/长期有效的直接列出证号与原件文件名（如有图片/扫描件附注“可从规则库下载原件插入”），缺失的标红提示 `[台账缺失，请补充上传]`；
   - **★/▲ 实质性响应与偏离表章节**：把提取的 `marked_clauses` / `scoring_tables` 转为结构化偏离表预制格与逐条响应模板，已接任务 F4 结论时同步填入响应摘要，未接时标 `[请技术/商务人员核对响应]`；
   - **技术实施方案大纲章节**：严格按招标《采购需求》及《评分细则》技术分项逐节生成目录，每节下附「评分得分点清单」与「拟响应子目录提纲」，避免漏点丢分。
3. **V2 方案库填肉插槽（`rag_knowledge` 预留接插口）**：
   - 定义清晰协议 `KnowledgeSnippetProvider`（默认实现可读取本请求可选传入的 `knowledge_paths` 切片，使用 `core/hybrid_retriever.py` 做局部检索）：
   - 当模式切为 `'knowledge_draft_v2'` 且提供历史优秀标书文件时，对技术方案各评分小节检索最相关历史片段，仅允许在 `client!=None` 时受控基于**检索出的局部片段 + 招标该条要求**做术语对齐改写（严禁引入未在参考片段和招标文件出现的业绩年份/虚构数据），且整段标灰/附注来源文件名供人工终核。
4. **Word 渲染与导出安全卫生**：
   - 输出标准 `.docx`（统一宋体/黑体清晰层级、自动页眉带项目名且严禁残留旧模板名称、表格全套边框规范渲染、未确认/待填项统一 `[待人工补充：...]` 醒目底色高亮）。

### §3.2 原位无损修订引擎：`core/redline.py` 新增 Clean 定稿导出

1. **接口签名**：
   ```python
   export_clean_revised_docx(
       bid_docx_path: str | Path,
       accepted_findings: list[dict[str, Any]],
       output_path: str | Path,
       *,
       replacements: Optional[dict[int, str]] = None,
   ) -> dict[str, Any]
   ```
   - 返回：`{'output_path', 'applied_count', 'manual_pending_count', 'applied_items': [...], 'manual_pending_items': [...]}`；
   - **确定性安全替换规则**：
     - 对每条 `accepted` 发现，仅当具备**明确可自动替换靶标**（用户前端传入的 `replacements[finding_id]` 明确新文本，或诸如 `CROSS_PROJECT_NAME` 在明确指定替换为当前招标项目名时，定位目标段落 run 执行局部字符替换，尽量保留首 run 字体/字号/加粗样式）；
     - 同步清理文内可能残留的 `w:commentRangeStart`、`w:commentRangeEnd`、`w:commentReference` 与 `comments.xml` 部件，确保导出件无任何审查批注痕迹；
     - 对缺少确定替换值或属于大段漏应答的结构性风险（如 `MISSING_RESPONSE` 且用户未填替换文本），绝不瞎改正文，诚实收入 `manual_pending_items` 供前端导出回执提醒。
